# Containerized Environment Investigation

**Source:** Coursework-derived case study, independently rewritten  
**Status:** Complete  
**Environment:** Authorized, isolated lab with sanitized identifiers

## Executive summary

I investigated unusual traffic in a containerized Linux lab after earlier reconnaissance and packet analysis identified repeated communications on a notebook-service port and several machine-learning outliers.

The investigation used file inspection, cryptographic hashing, packet review, system-call tracing, open-file inspection, process monitoring, and network capture. The evidence did not support a conclusion that malware executed. Several unusual records were explained by normal notebook traffic and IPv6 service-discovery behavior.

This distinction matters: an anomaly is a lead for investigation, not proof of compromise.

## Scope

- Containerized Linux systems in an isolated, authorized environment
- Self-generated packet captures and structured traffic data
- Static and live-response analysis
- No production systems, personal data, or live malware

All hostnames, addresses, hashes, dates, and school-specific details from the original report have been omitted or replaced.

## Evidence examined

- Packet-capture files
- Structured anomaly data derived from the captures
- File metadata and cryptographic hashes
- Running processes and open files
- Active sockets and observed network communications
- System calls generated by a benign test process

## Investigation approach

### Preserve and identify

I recorded the evidence set and generated multiple cryptographic hashes for integrity tracking. Public portfolio evidence will use only a newly generated sample so that old lab identifiers and provider data are not disclosed.

### Static analysis

I reviewed filenames, metadata, strings, traffic records, ports, packet sizes, and anomaly scores. Repeated communications on the notebook-service port were prioritized for deeper analysis.

### Live response

I used Linux tools to observe:

- System calls
- Open files and sockets
- Packet activity
- Running processes and child processes

Observed behavior was consistent with the expected notebook environment. I did not identify persistence, unauthorized file modification, suspicious child processes, or external command-and-control traffic.

### Packet-level validation

The anomalous dataset included multicast DNS and ICMPv6 discovery traffic. Packet inspection showed that these records were consistent with common service-discovery and network-discovery functions in the lab.

## Findings

1. The environment contained repeated internal notebook-service communications that were unusual relative to the dataset but not inherently malicious.
2. Some machine-learning anomalies were normal multicast and discovery traffic.
3. Live-response evidence did not show malware execution or persistence.
4. The anomaly model helped prioritize records, but analyst validation was required to avoid a false positive.

## Assessment

**Disposition:** No confirmed malware  
**Confidence:** Moderate  
**Reasoning:** Multiple evidence sources supported normal container and notebook behavior, but the exercise's limited observation window and synthetic environment prevent an absolute conclusion.

## Recommendations

- Establish an approved baseline for expected container-to-container traffic.
- Restrict notebook services to required interfaces and authenticated users.
- Retain packet and host telemetry long enough to correlate future alerts.
- Enrich anomaly records with process, user, and service context.
- Treat model output as triage input rather than an automatic incident verdict.

## Skills demonstrated

Evidence handling, hashing, packet analysis, Linux live response, process and socket inspection, anomaly validation, false-positive analysis, incident reporting, and confidence-based conclusions.
